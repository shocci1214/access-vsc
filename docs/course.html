学習コース

Access VSC を「使える」から「使いこなせる」へ。初級・中級・上級の 3 段階で、仕組みや考え方を理解し、自分の仕事のデータベースで実践できるようになることを目指します。

前提：チュートリアルを一度終えていること到達目標のチェックはこのブラウザに保存されます

このコースについて

レベルこんな人修了すると
初級チュートリアルを終えた人自分のデータベースで、毎日の開発を VS Code で安全に回せる

1. 仕組みを理解する

Access のデータベース（.accdb）は 1 つの大きなファイルで、中の VBA やクエリは Access でしか見られません。Access VSC は、中身を普通のテキストファイルに書き出し（取り出す）、編集したファイルをAccess に書き戻す（反映する）道具です。

なぜテキストにするの？

探せる

全モジュールから一度に検索・置換できる。「この関数はどこで使っている？」がすぐわかる。

比べられる

変更前と変更後を並べて見られる。何を変えたかが一目でわかる。

履歴が残る

git を使えば、いつ・何を変えたかが全部残り、いつでも戻せる。

AI が扱える

AI はテキストを読み書きするのが得意。Access の中身を AI に任せられる。

覚えておくこと

  • 正しいのは「動いている Access」：ファイルを編集しただけでは Access は変わりません。反映して初めて変わります
  • 「未反映」：ファイルを変えたが、まだ Access に入れていない状態。サイドバーとステータスバーに数が出ます
  • 見るだけのファイル：テーブル定義（tables/*.json）は参考用。編集しても DB は変わりません
  • 反映の前に自動バックアップ：.accessvsc\backups に最新 10 個が残ります
Q1. ファイルを編集して保存しました。Access のモジュールは変わっていますか？

変わっていません。「③ Access へ反映する」を押すと変わります。サイドバーには「● 変更あり（未反映）」と出ています。

Q2. テーブルに項目を足したくて tables/Customers.json を書き換えました。どうなりますか？

DB は変わりません（保存するとコードチェックで注意が出ます）。テーブルの変更は Access の画面か SQL（ALTER TABLE など）で行い、その後「取り出す」でファイルを最新にします。

Q3. Access で DB を開いたまま「反映する」とどうなりますか？

「データベースが Access などで開かれています」と出て反映されません。Access を閉じてから実行します。

2. 毎日の流れ

（必要なら）取り出す→編集・保存→反映（＋コンパイル）→実行・プレビューで確かめる→（区切りで）コミット
こんなときやること
朝、作業を始めるステータスバーの未反映の数を確認。0 ならそのまま編集を始めてよい
Access の画面でフォームのデザインを変えたAccess を閉じてから「① Access から取り出す」でファイルを最新にする
VBA を直した保存 → 「③ Access へ反映する」→ 赤い波線がなければ実行して確かめる
モジュールを削除したいファイルを削除 → 反映（Access からも削除するか聞かれる）
反映を忘れがち設定の Import On Save をオンにすると、保存するたびに自動で反映
「取り出す」と「反映」を取り違えないファイル側に未反映の変更があるのに「取り出す」と、その変更が上書きされる恐れがあります。Access VSC は確認を出しますが、迷ったら先に反映が安全です。

4. エラーと付き合う

種類いつ見つかる原因の例表示
コンパイル エラー反映したとき変数名の打ち間違い、End If の書き忘れ、存在しない関数の呼び出し赤い波線＋エラーの内容と行番号
実行時エラー実行したとき0 で割った、型が合わない、Null を数値として使ったエラーが起きた行に赤い波線＋エラー番号
コードチェック保存したとき（Access 不要）Shift-JIS で使えない文字、Option Explicit の書き忘れ、帳票のはみ出し赤（エラー）／黄（警告）の波線
  • エラーの一覧は Ctrl+Shift+M（問題パネル）。行をクリックするとその場所へ移動します
  • 実行中の MsgBox は自動で答え、内容は結果に記録されます（OK だけなら OK。「削除しますか？」のような確認には、安全側の「キャンセル」／「いいえ」）
  • InputBox やモーダルフォームは自動で答えられないため、時間切れになって Access が終了します（上級「直しやすい VBA の設計」で対策を学びます）
  • 絵文字や一部の記号は Access に入れると ? に化けます（コードチェックで赤い波線）
演習 2次の表示が出ました。それぞれ、何をすればよいですか？
  1. 「コンパイル エラー: Sub または Function が定義されていません。（modOrder.bas の 12 行目）」
  2. 「実行時エラー '94': Null の使い方が不正です。」
  3. 「データベースが Access などで開かれています。」
解答例

  2. Null の値を文字列や数値の変数に入れている。Nz(値, 0) などで Null のときの値を決める。
  3. Access の画面で同じ DB を開いている。閉じてから、もう一度実行する。

5. 自分のデータベースで始める

練習が終わったら、いよいよ自分の仕事のデータベースです。最初に次の順で準備すると安全です。

  1. データベースをコピーしておく念のため、手作業でもコピーを取っておきます（Access VSC の自動バックアップとは別に）。
  2. 専用のフォルダに入れる例：C:\work\在庫管理\在庫管理.accdb。そのフォルダを VS Code で開きます（デスクトップ全体などを開かない）。
  3. Access を閉じて「① Access から取り出す」オブジェクトが多いと数分かかることがあります。
  4. 気になる点を確認
    • AutoExec マクロやスタートアップ フォームがあると、操作のたびに動きます。何か処理をしている場合は注意
    • リンクテーブルの先（バックエンド）は本物のデータです。テストや SQL で書き換えないように
    • ODBC など外部接続のパスワードは、取り出したファイルでは *** に伏せられます
  5. git を始める「テスト・品質」→「テスト・CI/CD を準備」で git も始められます（中級「git で履歴を残す」）。
やってはいけないこと
  • フォーム・レポートの PrtMip や PrtDevMode、0x... が並ぶ行を編集する（壊れます）
  • 同じ DB を Access で開いたまま、VS Code から反映する
  • テーブル定義（.json）を編集して変わったつもりになる
Q. 取り出したら ? が混ざった行がありました。なぜ？

Access の中で既に Shift-JIS で表せない文字が化けていた可能性があります。Access VSC が化けさせたわけではありません。正しい文字に直して反映してください。

中級思いどおりに直し、壊していないと言える

1. 帳票レイアウトの考え方

帳票のテキストの読み方

Begin Report
    Width =8000                 ← 帳票全体の幅
    Begin
        Begin PageHeader        ← ページヘッダー（毎ページの上）
            Height =1100        ← セクションの高さ
            Begin
                Begin Label     ← 項目 1 つ分（ここから End まで）
                    Left =300   ← 左端からの位置
                    Top =100    ← セクションの上端からの位置
                    Width =4000
                    Height =450
                    Name ="lblTitle"
                    Caption ="受注一覧"
                    FontSize =14
                End
            End
        End
        Begin Section           ← 詳細（1 件ごとに繰り返す）
            ...

twip（トゥイップ）

長さの単位。1 cm = 567 twip、1 mm ≒ 57 twip。

セクション

ページヘッダー（毎ページ上）・詳細（1 件ごと）・ページフッター（毎ページ下）など。Top はセクション内の位置。

帳票の幅

Begin Report 直下の Width。項目がはみ出すと Access が自動で広げる。

印刷可能幅

用紙の幅 −（左余白 + 右余白）。帳票の幅がこれを超えると白紙ページが出る。

白紙ページが出るしくみ

A4 縦（幅 21 cm）で左右の余白が 10 mm なら、印刷可能幅は 19 cm（10,773 twip）。帳票の幅が 19 cm を少しでも超えると、はみ出した部分が次のページに印刷され、何も載っていない白紙のページが交互に出ます。プレビューの「印刷可能幅を超えています」はこのことです。

直し方は 3 通り：項目を詰めて帳票の幅を縮める ／ 余白を小さくする ／ 用紙を横向きにする（ページ設定）。

おすすめの手順プレビュー → 「レイアウト詳細」で各項目の位置（cm）を確認 → テキストを編集 → 反映 → プレビュー。帳票を直したら「帳票の見た目を比較」で、ほかの帳票まで変わっていないか確かめます。
演習 3A4 縦、左右の余白 15 mm の帳票があります。帳票の幅が Width =11000 のとき、白紙ページは出ますか？
解答例

印刷可能幅は 210 − 30 = 180 mm = 18 cm = 約 10,206 twip。11,000 はこれを超えるので白紙ページが出ます。約 800 twip（1.4 cm）詰めるか、余白を左右 8 mm 以下にするか、横向きにします。

2. AI と協働する

AI は、ファイルを読んで直し、Access に反映し、エラーがあれば直し、実行・テスト・プレビューで確かめる、までを自分で繰り返せます。人の役割は「何をしたいかを正しく伝える」ことと「結果を確かめて受け入れる」ことです。

頼み方の型：目的・条件・確かめ方

伝わりにくい

請求書を直して

税計算がおかしい

伝わりやすい

rptInvoice の金額列が右端で切れている。金額列の幅を広げて、A4 縦に収まることをプレビューで確認して。

TaxIncluded(99) が 109 を返すが、仕様は 1 円未満切り捨てなので 108 が正しい。直して、テストを追加して通ることを確認して。

任せてよいこと・人が判断すること

任せやすい人が判断する
関数の追加・修正とテスト、帳票の位置・大きさの調整、クエリの作成、エラーの原因調査、コードの整理仕様そのもの（何が正しいか）、本番データの更新、配布、帳票の見た目の基準の更新、セキュリティに関わること

結果の確かめ方

  1. ［ソース管理］で差分を見る：変わったファイルと行を確認
  2. テストを実行：AI が書いたテスト＋既存のテストが通るか
  3. 帳票の見た目を比較：意図しない帳票まで変わっていないか
  4. Access で開いて触ってみる：フォームの動きなど、テストしにくい所
「できました」は結果で確かめるAI への作業手順には「完了の条件」（反映が成功し、取り込みの確認で抜けがない・テストの失敗 0・コードチェックのエラー 0・帳票は画像で確認）が入っています。AI の報告に、実行したツールとその結果（テストの件数など）が書かれているかを見てください。結果が書かれていない「できました」は、まだ確かめていない可能性があります。
プロジェクトのルールを AI に覚えさせるCLAUDE.md（Copilot なら .github/copilot-instructions.md）に、命名規則や「金額は Currency 型」などのルールを書き足すと、AI が毎回それに従います。

3. git で履歴を残す

コミット

「ここまで」の区切りで変更を記録すること。メッセージを付ける。

差分

前回のコミットから何が変わったか。［ソース管理］でファイルをクリック。

取り消し

ファイルの変更を最後のコミットの状態に戻す（［変更を破棄］）。

履歴

過去のコミットの一覧。いつ・誰が・何を変えたか。

Access 開発での使い方

  • コミットするもの：ソースフォルダ（*.accdb.src）と .accdb。.accessvsc（作業用）はコミットしない（自動で除外設定されます）
  • コミットの単位：「税計算を直した」「請求書の列を広げた」のように、1 つの目的ごと
  • 変更を取り消したい：［ソース管理］でファイルを右クリック →［変更を破棄］→ 反映（ファイルを戻しただけでは Access は戻りません）
  • コミット前のチェック：テスト・CI/CD の準備をすると、コミットのたびにコードチェックが自動で走り、エラーがあると止めてくれます
演習 4AI に頼んだ修正が気に入りません。AI が触る前の状態に戻すには？（AI に頼む前にコミットしてあるとします）
解答例

［ソース管理］で変更されたファイルをすべて選んで［変更を破棄］→「③ Access へ反映する」。新しく作られたファイルは削除し、反映時に「Access からも削除する」を選びます。AI に頼む前にコミットしておくと、こうして簡単に戻せます。

4. テストの考え方

何をテストするか

  • 計算（税・割引・合計・日付計算）、判定（入力チェック・区分の決定）、文字列の加工（コード生成・書式）
  • 境目：0、負の数、空文字、Null、最大値、月末・うるう年
  • 直したバグ：バグを直す前に「そのバグで失敗するテスト」を書くと、二度と同じバグが出ない

テストしやすくするコツ

フォームのボタンの中に計算を直接書くと、テストできません。計算は標準モジュールの関数に切り出し、フォームはそれを呼ぶだけにします（上級「直しやすい VBA の設計」）。

データを使うテスト

Public Sub TestSetup()          ' 各テストの前に呼ばれる
    CurrentDb.Execute "DELETE FROM Orders", dbFailOnError
    CurrentDb.Execute "INSERT INTO Orders (OrderDate, CustomerID, ProductID, Qty) VALUES (#2026/4/1#, 1, 1, 10)", dbFailOnError
End Sub

Public Sub Test_OrderTotal()
    Assert.AreEqual 1500, DSum("Qty * 150", "Orders")
End Sub

テストはデータベースのコピーで動くので、データを消しても元の DB は無事です。ただしリンクテーブルの先（バックエンド）は本物なので、データを書き換えるテストは、テスト用のバックエンドにリンクした状態で行います。

演習 5次の関数のテストを、境目も含めて 3 つ以上書いてください。 
' 数量に応じた割引率（10 個以上 5%、50 個以上 10%）
Public Function DiscountRate(ByVal qty As Long) As Double
    If qty >= 50 Then
        DiscountRate = 0.1
    ElseIf qty >= 10 Then
        DiscountRate = 0.05
    Else
        DiscountRate = 0
    End If
End Function
解答例 
Public Sub Test_Discount_9()
    Assert.AreClose 0, DiscountRate(9)
End Sub
Public Sub Test_Discount_10()          ' 境目
    Assert.AreClose 0.05, DiscountRate(10)
End Sub
Public Sub Test_Discount_49()
    Assert.AreClose 0.05, DiscountRate(49)
End Sub
Public Sub Test_Discount_50()          ' 境目
    Assert.AreClose 0.1, DiscountRate(50)
End Sub

小数の比較は AreClose を使うと、計算誤差で失敗しません。

Q. テストが全部 ✔ なら、バグはないと言えますか？

言えません。「テストで確かめたことは正しい」と言えるだけです。大事な計算や過去にバグが出た所から、少しずつテストを増やしていきます。

1. 品質を仕組みにする

「気をつける」ではなく「仕組みで防ぐ」ために、チェックを何段階かに分けます。

いつ何が動く見つけるもの速さ
保存したときコードチェック使えない文字、Option Explicit、Stop、帳票のはみ出し数秒
反映したときコンパイルVBA の文法・参照の間違い10 秒前後
コミットするときコードチェック（コミット前フック）エラーのある状態での記録を防ぐ数秒
GitHub に送ったときCI：取り込み・コンパイル・テスト・帳票の見た目の比較壊れた状態がチームに広がるのを防ぐ数分

チームのルール例

  • 全モジュールに Option Explicit（コードチェックが警告）
  • 計算・判定は標準モジュールの関数にし、テストを付ける
  • 帳票の基準画像の更新は、見た目の変更が意図どおりかを別の人が確認してから
  • CI が ✘ のまま main に入れない（GitHub のブランチ保護で「CI 成功を必須」にできる）
日付を印刷する帳票印刷日を表示する帳票は、比較のたびに少しずつ変わります。CI の比較では -Threshold 0.1（変化したピクセルが 0.1% 以下なら同じとみなす）を使います。

2. CI（自動チェック）

「テスト・CI/CD を準備」で作られる .github/workflows/access-ci.yml は 2 つのジョブからなります。

ジョブ動く場所内容
lintGitHub のクラウド（設定不要）コードチェック
testAccess の入った PC（セルフホストランナー）ソースをすべて取り込み → コンパイル → テスト → 帳票の見た目の比較 → 結果を成果物に保存

セルフホストランナーの用意

  1. 専用の Windows PC（または仮想マシン）を用意Access をインストールし、ライセンスを確認。人が普段使う PC とは分けるのがおすすめ。
  2. リポジトリ →［Settings］→［Actions］→［Runners］→［New self-hosted runner］表示される手順で登録し、ラベル access を付ける。
  3. ログオンしたユーザーとして run.cmd を起動しておくサービスとして動かすと、Office の自動操作が正しく動きません（自動ログオン＋スタートアップに登録するなど）。

失敗したときの読み方

  • 注釈：プルリクエストの「Files changed」で、エラーの行に直接表示されます
  • 概要：ジョブの Summary に、失敗したテストと帳票の一覧
  • 成果物：access-test-results に JUnit の結果と帳票の差分画像（違う所が赤）
Q. 手元ではテストが通るのに、CI では失敗します。何を疑いますか？

(1) 未反映・未コミットのファイルがないか（CI はコミットされた .accdb にソースを取り込みます）。(2) .accdb をコミットし忘れていないか。(3) データに依存するテストが、手元の DB にしかないデータを前提にしていないか（TestSetup でデータを用意する）。

3. 配布と運用

フロントエンドとバックエンド

画面・クエリ・VBA の入った フロントエンド と、テーブル（データ）だけの バックエンド に分けておくと、データに触れずにプログラムだけ差し替えられます。Access VSC の配布は、この形を前提にしています。

リリースの流れ

配布の設定（1 回）→リリースを作成→配布する→利用者は起動するだけ
  • リリースを作成：DB をコピー → 版番号（AppVersion）を書き込み → リンクテーブルを本番のバックエンドに張り替え → コンパイル → .accde
  • 配布する：共有フォルダの app\ を差し替え、releases\<版>\ に保管、version.json を更新
  • 利用者：共有フォルダの Start-<アプリ名>.cmd から起動すると、新しい版があれば自分の PC にコピーしてから開く
  • 戻す：「配布する」で dist の前の版を選んで配り直す

運用のコツ

  • アプリの画面のどこかに版番号を表示する：CurrentDb.Properties("AppVersion")。問い合わせのときに「どの版か」がすぐわかる
  • タグ（v1.2.0）を付けて push すると、取り込み → テスト → リリース → 配布までを CI で自動化できる（access-release.yml）
  • .accde は作った Access と同じビット数（32 / 64 bit）でしか動かない。利用者の Office に合わせる
  • セキュリティの警告が出る場合は、管理者に %LOCALAPPDATA%\AccessApps を「信頼できる場所」に登録してもらう（グループポリシーなど）

4. 直しやすい VBA の設計

テストしやすく、AI にも任せやすく、自動化で止まらない VBA にするための考え方です。

画面・ロジック・データを分ける

分かれていない

' フォームのボタンの中に全部
Private Sub cmdCalc_Click()
    Dim total As Currency
    total = Me.txtPrice * Me.txtQty
    If Me.txtQty >= 10 Then total = total * 0.95
    Me.txtTotal = Int(total * 1.1)
    MsgBox "計算しました"
End Sub

分かれている

' modPrice.bas（テストできる）
Public Function OrderTotal(ByVal price As Currency, _
                           ByVal qty As Long) As Currency
    Dim total As Currency
    total = price * qty * (1 - DiscountRate(qty))
    OrderTotal = TaxIncluded(total)
End Function

' フォームは呼ぶだけ
Private Sub cmdCalc_Click()
    Me.txtTotal = OrderTotal(Me.txtPrice, Me.txtQty)
End Sub

そのほかのコツ

  • ロジックの中で MsgBox・InputBox を使わない：画面側で表示し、関数は値を返すだけにする（自動実行で止まらない・テストできる）
  • 税率などの決まりごとは定数か設定テーブルに：Public Const TAX_RATE As Double = 0.1
  • エラー処理の型をそろえる：画面側で On Error GoTo して利用者向けのメッセージ、ロジック側はエラーをそのまま上げる
  • Null に備える：フォームの値やテーブルの値は Nz() で受ける
  • 小さな関数：1 つの関数は 1 つの仕事。名前で何をするかわかるように
演習 6（総仕上げ）自分のデータベースから、フォームのボタンの中で計算している処理を 1 つ選び、標準モジュールの関数に切り出してテストを書いてください。AI に頼んでも構いません（「cmdCalc_Click の計算を modPrice の関数に切り出して、テストも書いて、フォームの動きが変わらないようにして」）。
